# 買い物コードレビューとホーム整理（2026-10-07）

買い物一覧、チェック保存、数量編集、削除、購入確認への移動、ホームへの影響をレビューし、余分な読み込み・表示更新を減らした。開発場所は iCloud外 `${HOME}/Developer/IOSアプリ制作`。旧iCloudコピーは変更しない。

## レビューで見つけた問題と修正

| 箇所 | 問題・影響 | 修正 |
| --- | --- | --- |
| ShoppingViews.swift のQuery | 冷蔵庫へ登録済みの履歴も取得し、表示のたびに除外。履歴が増えるほど読み込み・モデルの作成が増える。 | 未登録だけをDBのpredicateで取得。登録済みの履歴は削除しない。 |
| ShoppingViews.swift の一覧構築 | 全件除外、フィルター、2分類、購入件数を別々に再走査。同じ行のチェックを繰り返し参照し、他の商品も行内容を再構築する。 | 表示対象を1回で分類・集計。表示値をスナップショットにしてEquatable行へ渡し、変わらない行のbody再評価を抑える。行全体のタップ・スワイプ・アクセシビリティは保持。 |
| RecipeViews.swift のHomeView | 買い物Queryをホーム全体が持ち、チェック保存で141料理の候補計算も更新し得る構造。 | 買い物の小さなサマリーだけにQueryを分離。未購入だけを取得し、件数・先頭3品の表示を保持。 |
| InventoryUndo.swift のclear | Undoがない状態でも同じnilをPublishedへ設定。チェック保存ごとにRootViewへ不要な通知を送る。 | 空のclearを何もしない処理にした。実際にUndoがある場合の無効化・新しいUndoの保護は維持。 |
| ShoppingChecks.swift | 同じ保存中IDの再insert、保存完了時の同じチェック状態の再代入、確定済みoverrideの個別削除が余分な表示通知を出す。 | 値が変わる場合だけ公開。確定済みoverrideの除去をまとめる。保存順・最後のタップ優先・失敗復元・購入前flushは保持。 |
| MealService.swift の手動追加・数量編集・削除 | 在庫を変えていない操作でも期限通知の再計算を起動。編集・削除は全買い物行からIDを探す。 | 3操作の在庫変更通知を抑制。編集・削除は対象UUID・未登録条件・fetchLimit1。編集のマスター単位確認も対象IDだけ取得。購入・調理・Undoの通知は維持。 |
| 購入確認を開く間 | 保存待ち中の反応が分かりにくく、別の追加・編集操作を始められる。 | 保存中の表示とProgressViewを付け、確認へ移る間は追加・フィルター・編集・削除・追加チェックを止める。二重実行も防止。 |

チェック自体は引き続き保存前に表示へ反映。保存処理は専用のメイン外キューで、UUID・Boolだけを渡す。購入を確定する前にチェック保存を待ち、失敗した場合は購入へ進めない。軽量化のために保存や在庫検証を省略していない。

## ホーム

見出しを「今日何作る？」へ変更。期限切れ食材の一覧をホームから削除し、期限が近い食材の一覧は残した。期限切れは右上の通知一覧とマイ冷蔵庫で確認・編集できる。献立計算からの期限切れ除外は保持し、食材自体を消したり期限を変えたりしない。

## 測定

Simulator iOS27のディスク保存で、登録済み2,000件＋未登録50件を作成し、新しいModelContextで10回取得した。

- 初回：全2,050件取得→アプリで除外の中央値24.34ms、未登録50件だけ取得0.75ms。
- 修正済み関連テストの再実行：27.11ms → 1.04ms。2,050件すべての保存が残り、表示対象のIDと順序が一致することも確認。
- Undoがないチェック成功ではUndoの公開通知0回。チェックの保存完了で同じoverrideを再通知せず、Queryへの同期は1回だけ公開することを検証。

測定値は一覧の取得処理で、実機のタップ遅延・描画フレームの測定ではない。実機の体感は更新後に確認する。今回、購入確定の一括在庫登録・Undo用の保存やスナップショットまで非同期化する変更は行っていない。
