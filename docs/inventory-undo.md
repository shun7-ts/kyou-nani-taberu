# 在庫操作の取り消し

各タブの下部に、最後に保存した操作の「取り消す」を表示する。確認画面で取り消すと、その保存1回分をまとめて戻す。キャンセルすれば保存後の状態と案内を保つ。案内の×は取り消し情報を破棄するだけで、保存データは変えない。

## 対象と戻る内容

| 操作 | 取り消した結果 |
|---|---|
| 手入力・初期在庫・レシート・音声から追加 | 新しく追加したロットを一覧から取り除く。合算した既存ロットは元の量へ戻す |
| 数量・保存方法・購入日・期限を修正 | 修正前の正確／曖昧状態、数量・単位、保存方法、購入日、期限・期限種別へ戻す |
| 取り除く・取り除いた食材を戻す | 元の表示／取り除いた状態へ戻す |
| 購入品の一括登録 | 追加・合算を戻し、対象購入品の「在庫へ登録済み」を解除する。購入チェックは保つので再確認できる。日用品だけの登録も取り消せる |
| 調理完了 | 差し引いた全ロットの量・曖昧状態と、献立の「選択済み」を戻す。再び使用量を確認して調理完了にできる |

追加の取り消しは完全削除ではない。自分用食材と元の履歴は残り、設定の「取り除いた食材を戻す」から復元できる。取り消し自体も履歴へ追加する。レシート／音声の保存済みセッション印を残すため、同じ確認結果を再送して重複登録することはできない。新しく読み取り・入力して確認すれば再登録できる。

同意、OS許可、初期登録完了の設定は戻さない。初期在庫の取り消し後は設定から一括登録をやり直せる。

## 保持期間と競合

取り消し情報は端末のメモリだけに保持し、DBやUserDefaultsへ保存しない。新しい在庫操作の保存に成功すると置き換わる。変更のない一括登録と保存失敗は前の案内を保つ。献立の変更や買い物行の追加・修正・チェック・削除に成功した場合は、関連状態の食い違いを防ぐため取り消し情報を消す。

1回を取り消すと案内を消す。複数回さかのぼる操作・Redo・再起動後の取り消しは対象外。全データ削除のコミットに成功したら取り消し情報も消す。削除が失敗した場合は保つ。

戻す前に、影響を受けた在庫・購入品・献立の保存後の値が現在値と一致するかを確認する。1件でも変更・欠落があれば全体を拒否し、現在の値を上書きしない。数量だけでなく保存場所、期限、削除状態、バージョンや購入・献立の状態も比較する。

専用ModelContextで一括保存し、失敗した場合は全変更をロールバックする。保存失敗なら再試行できる。取り消し時も在庫のsyncVersionと更新日時を進め、取り消し前の古い音声確認が有効へ戻らないようにする。成功後は期限通知の再計算を要求する。

## 構成

`InventoryUndoCenter`はModelContainerごとに1件の取り消し情報を持つ。登録先は弱参照で、通常DBとテストDBの情報が混ざらない。保存サービスは共通トランザクションを使い、保存が成功した後だけ情報を更新する。保存前後には在庫・献立・買い物の値を取得し、保持するのは変更したレコードだけ。食材マスターの複製、写真・音声・OCR原文の保持、SwiftDataスキーマの追加は行わない。

単体テストでは全フィールド復元、追加の取り除き、廃棄／復元、一括登録、直前1回、競合、保存失敗、レシート合算・重複防止、購入、調理、古い音声確認、全削除、DBごとの分離、期限通知の再計算を検証する。画面テストではキャンセル、在庫編集の取り消しと履歴、購入と調理を取り消した後の再確認を検証する。
